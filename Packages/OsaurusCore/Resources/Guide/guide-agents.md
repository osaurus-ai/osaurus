# Agents

Agents are the core of Osaurus. Each agent has its own system prompt, default model, tool grants, memory, and look. The built-in "Osaurus" default agent — the Orchestrator — configures the app, answers questions about it, and delegates work to your custom agents; custom agents do everything else (see The Orchestrator topic).

## Creating and managing agents

- **New Agent** (Settings → Agents header, the empty Agents page, the **+** beside Agents in the chat sidebar, or the "own agent" discovery tip) opens the **New Agent** page in Settings → Agents, with **‹ Agents** to step back to the list. Settings' sidebar collapses while it shows. It starts with one question, "What should your new agent do?": describe it in the message box, pick an idea (Assistant, Writer, Researcher, Coder, Productivity), or choose **Fill it in yourself instead**. A Describe → Shape → Create stepper shows where you are.
- Once you start, the chat with the Configurator leads and the agent's card sits beside it. The card starts with just a name and look; **Instructions**, **Tools** and **Model** join it as the Configurator drafts them (it gives a short reason for each tool it turns on and asks at most a couple of questions), and the part it just changed is briefly marked. Parts not on the card yet are listed under **Still to come**, where you can add them yourself.
- Every part has **Edit** (Tools has **Customize**, which opens the tool picker in a sheet: Auto or Manual mode, hand-picked tools, Apple apps). A field you edit is marked **Edited by you** and the Configurator keeps your value. In a narrow Settings window (for example with the sidebar opened again) the chat and the card stack behind a **Chat** / **Agent** switch.
- Nothing is saved until you click **Create Agent** (it needs a name no other agent uses). Settings then opens the new agent's page with **Start Chatting**, and the Set Up Agent wizard (the same one a template uses) when the agent still needs something on this Mac. Generation Overrides and **Show Response Metrics** are on the new agent's page (General → Configure → Advanced Settings).
- A draft you step away from waits: the Agents list shows it with **Continue** and **Discard**, also after a relaunch, and **New Agent** continues it. The New Agent page's ⋯ menu has **Discard Draft**.
- With no model set up, the first screen says so and offers **Choose a Model**; **Fill it in yourself instead** still works, so you can fill in the card and click **Create Agent**.
- Settings… (⌘,) → Agents → edit or delete agents.
- Or ask the default Osaurus assistant: "create a coding agent" — it can create, update, and switch agents for you.
- Switch agents from the agent menu in the chat window.

## Agent templates (Agents → Templates)

- A template is one agent's configuration as portable JSON: prompt, model, tool selection (MCP servers and plugins by name), sandbox, subagent settings, and a `requires` list of what the author relied on (working folder, knowledge collections, plugins, MCP servers, permissions, model). Secrets, folder access grants, and knowledge files never travel.
- Save one from any agent card (⋯ → Save as Template). After saving, the sheet shows **Saved** with **Share…** (opens Templates with Share up for it) and **Done**. Import one with the **Import Template** button, by pasting JSON, by dropping a `.osaurustemplate` (or `.json`) file on the Templates page (the **Templates** button in the Agents header), or with **Install agent** on a store.osaurus.ai page (an `osaurus://templates-import?url=…` link opens the same import review on this page, showing the host it came from).
- Share one with the **Share** button on its card (also in its **…** menu as **Save as File…** and **Publish…**). Share offers two ways: **Save as a file** writes a signed `.osaurustemplate`; **Publish to store.osaurus.ai** publishes the same signed file as a page at store.osaurus.ai/a/… that you own: it needs an Osaurus ID, you set **Listing Details** (the page's **Name** and **Description**), up to 3 **Topics**, and **Example Runs** (**Add Example Runs…** lists conversations with agents made from the template: the first request, the reply, and the images it shared, each previewed under **What leaves this Mac**; you confirm before any are shared), you choose **Who can see it** (Public, Unlisted, or Password), and workflows the template carries go with it inside the signed file. Under **Also publishes** the sheet lists each one: **Give my workflows their own pages** (on by default) first publishes the ones that are yours and not live yet as their own workflow pages with the agent's visibility (Public or Unlisted; a password-protected agent keeps them bundled only), so the agent's page links to each with **Its own page**, and each workflow page lists the agent under **Used by agents**. A workflow by someone else is never republished; the agent's page links to the original author's page when it carries that exact version. When it's done the sheet lists **Workflows it brings** with **Open Page** for each. The published dashboard has the same **Workflows it brings** list with **Open Page** and **Take Down…** per workflow; taking the agent down leaves those pages up. Changing the agent's **Who can see it** to Public or Unlisted shows **Also change its workflows** (on by default): Save moves the workflow pages published with it to the same, except ones you protected with their own password; a password-protected agent leaves them as they are. Afterward the card's button reads **Live · Public · N installs** and opens the published dashboard (**Installs**, versions, who can see it, **Listing Details**, **Topics**, and **Example Runs** with **Save Listing**, **Take Down**); the menu has **Manage Published…**, **Publish Version N…** when the template has changed, **Copy Link**, **Open Page**, and **Take Down…**; **Publish Again** brings a taken-down page back at the same link. Built-in templates show **Export** (and **Export File…** in the menu); **Save to Library** first to publish your copy.
- Once a template is published, a **N published · M installs · Your author page** line sits above the grid, and **All**, **Published**, **Built-in** and **Yours** chips (each with a count) narrow it. The chips also appear when more than eight templates are in the library. Adding a template from a published page counts once per Osaurus ID toward its installs, with the same signed receipt a workflow install sends. The workflows it brings into your library count toward their own pages' installs too, when the agent's page links to them.
- Use Template opens the Set Up Agent wizard on the template. Anything the template needs that this Mac does not have yet (a folder to pick, an MCP server to add) is a step there before **Create**.
- "Available to the Orchestrator" (toggle on the card) lets you say "make me an agent from the Cloud Agent template that does X"; the Orchestrator bases the new agent on the template instead of enabling every tool.
- Templates live in `~/.osaurus/template-library/<template-id>/v<N>.json` (one file per version); what this Mac published is remembered in `~/.osaurus/template-library/registry.json`. Whole-config YAML templates saved by `osaurus_config export` stay in `~/.osaurus/templates/`.

## Per-agent features (agent → Abilities)

- Tools (on by default) and Memory (on by default).
- Off by default, opt in per agent: Charts, Voice output, Calculator (exact arithmetic, `calculator_enabled`), Redaction Tools (`detect_pii` / `redact_file` in working-folder chats, `redaction_tools_enabled`), Memory Recall (search past memory), Self-scheduling, Computer Use, Database (per-agent private SQLite), Knowledge collections, sandbox execution options. Turn Calculator on for agents that work with numbers: finance, budgets, invoices, data analysis.
- On by default, can be switched off per agent: Share Artifacts (`share_artifact` file cards, `artifacts_enabled`), Task Checklist (`todo` + `complete`, `task_checklist_enabled`), Clarifying Questions (`clarify`, `clarify_enabled`).
- Working Folder: the one folder the agent works inside. Picking a folder with the chat Folder chip — or in the picker the agent itself opens with `prompt_working_folder` when a folder-less chat needs files — remembers it on the agent, so new chats, automations, and other background runs without their own folder start there; it also grants remote agent runs file access confined to that folder. Inside it, `file_read` handles every file type (text, PDF, Word, PowerPoint, Excel preview, images for vision models or via OCR) and `file_write` generates `.xlsx`, `.docx`, and `.pdf` as well as text — see the Chat topic, "File formats the folder tools handle".

## Channels and automations (agent → Channels, agent → Automation)

- **Channels** tab: a read-only **On Channels** list — "Slack: answers in #support, replies automatically, posts after asking first" — one row per channel the agent is on, each with **Edit in Channels**. Who answers on a channel and whether replies are sent automatically are set on the channel itself (Settings → Channels → the platform → **Routing**); whether the agent may post on its own is under **Sending** → **Agents that post on their own** (see the Agent Channels topic).
- **Automation** tab: the schedules, folder watches, webhooks, feeds, streams, failure handlers and app events that run this agent, plus **Add Automation** with it preselected (see the Automations topic). The built-in Default agent cannot run automations or answer channel messages; it can only be added to a channel as posts-only.

## Skills per agent (agent → Abilities → Tools)

- Skills come from the shared library (**Skills** in the sidebar). By default every custom agent can use every installed skill.
- **Limit to selected skills** above the tool picker narrows that to a list: only ticked skills appear in the agent's prompt, `capabilities_load`, and its slash commands. Turning it on starts with every installed skill ticked; **Choose Skills…** opens the checklist. A listed skill that is not installed here is flagged **not installed** and starts working once it is installed (for example by an `osaurus import` bundle).
- In config YAML this is `agents[].skills`: omit it to leave it unchanged, `null` for all skills, a list (skill names or slugs) for only those. Templates and bundles carry the list; the Templates review shows missing skills as an advisory.

## Runtime (agent → Configure → Runtime)

- **Runs on** chooses who runs the agent's chats: Osaurus (built-in), or a harness registered under Settings → **Agent Runtimes**, such as Claude Code, Pi, or a Pi-based harness. The chat model picker lists the same runtimes as columns, so you can switch from the composer; it changes this setting for the agent.
- On a harness, each chat is a long-running process in the chat's folder that brings its own model, tools, and history. The agent's system prompt is passed to Claude Code and to Pi (with `--append-system-prompt`, unless the runtime's arguments place `{system_prompt_file}` themselves); Osaurus abilities, memory, and the sandbox don't apply.
- In Claude Code's Agent mode, Claude sees only the built-in tools you allowed in the agent's Claude Code Options: Read, Grep, and Glob always; Edit/Write/NotebookEdit with **Allow file changes**; Bash and Monitor with **Allow shell commands**. WebFetch, WebSearch, sub-agents, and agent-team tools are never offered. A call Claude Code still refuses (for example, an edit outside the chat folder) shows a tool card naming the setting to change, and a call to a tool the run doesn't have says so.
- The Architect can run on Claude Code or Pi too. It keeps its own instructions and gets only its workflow tools (draft, test, runs, discover, propose save, and Osaurus inspect) over the Osaurus server, with none of the harness's file, shell, or web tools; the Claude Code Options don't apply to it. The draft panel fills in as on Osaurus's own loop, test runs ask their questions in the chat, and a proposed save shows the Save card when the reply ends. The Osaurus server must be running; otherwise the Architect says it can't build until it is.
- Harness agents can't be delegated to or run through `/agents/{id}/run`, Computer Use, or AppleScript yet; those return an error naming the harness.

## The Orchestrator (default agent) vs custom agents

- The Orchestrator configures and explains Osaurus, answers short questions inline, and delegates everything else to the agents you allow. It has a working folder it can **read** (`file_read`, `file_search`) but no shell, sandbox, browser, computer use, skills, knowledge, or media tools — that keeps setup safe and predictable.
- For hands-on work (edit files, run code, browse, generate images) the Orchestrator delegates to a custom agent. An agent without its own working folder works inside the Orchestrator's folder, so a fresh agent can write deliverables there right away. You can also switch to the agent and work with it directly.
- Custom agents get the full capability surface, gated by your per-agent feature toggles and tool permissions. Delegated agents run with their normal tools; only the delegation tool itself is withheld from a worker.
- New agents the Orchestrator creates with no model default to its current model. `template: coder | researcher | writer | assistant | productivity` fills in the system prompt and a routing description; a `description` is optional and is generated in the background from the system prompt when omitted; Settings → Agents → Delegation → **Create starter agents** makes Coder, Researcher, and Writer in one click.

## Agent identity and settings

- Each agent can have its own avatar, greeting, quick actions, and voice. Appearance (System, Light or Dark) is app-wide, under General → Appearance.
- When an agent needs you — a tool approval, a question, a workflow form, a teammate's request on a shared agent — it raises one request that reaches you in the app (Inbox → **Needs You**), as a desktop notification, and on your iPhone, as set in Settings → General → **Notifications**. Answering on any of them clears the others. A shared agent can wait for your approval of a teammate's tool call (**Require Approval for Teammate Tool Calls**), and you can write into a teammate's conversation with it; see the Workspaces topic. People are named by `@handle · 0x…` address, agents by name and address.
- Custom agents are stored as JSON under `~/.osaurus/agents/<uuid>.json`. The Orchestrator's own settings (name, persona, temperature, max tokens, delegation helpers) live in Settings → Orchestrator, or ask the assistant to change them.

## Generation overrides for each custom agent

Open a custom agent → General → Configure → Advanced Settings → Generation Overrides (a new agent gets them after **Create Agent**, on its page). Each field can inherit existing defaults or use a custom value. Temperature and Max Tokens keep their existing saved fields; Top P, Top K, Min P, repetition/frequency/presence penalties, seed, stop sequences and template parameters are saved with the same agent.

The selected model is inspected for its supported Thinking switch and exact Reasoning effort choices. An effort from a different model cannot be saved until it is changed to a supported choice or Inherit. No effort ladder or independent thinking-token budget is invented when the model has no such contract. The model's shared settings are never changed by this editor.

Use Save generation defaults to keep them. Defaults apply to chat, scheduled work and delegated execution. Explicit request/workflow values win; delegation limits can tighten an agent's Max Tokens. A submitted turn freezes its settings for tools, queued work and regeneration. External harnesses own their generation settings and do not use this section.

Agent export, templates and config apply carry the defaults. In YAML, temperature and max_tokens keep their existing fields. generation_settings contains the other optional snake_case fields. Omit the group to preserve it, use null to clear it, or supply a replacement group. template_kwargs accepts a JSON object; conversation, tools and special-token variables are reserved.

Max Tokens and Max output tokens per subagent cap total generated output per model turn, including reasoning. A model can exhaust the limit before producing a final answer. This cap does not reserve answer tokens and is not a separate thinking budget.

## Subagents and delegation

Custom agents can delegate work to other agents with `spawn_agent` — several calls in one message run in parallel as one wave — with limits and permission modes you control. The Orchestrator hands work to its allowed subagents through `run_workflow` instead (see the Orchestrator topic). Targets are your custom agents and, in workspaces you belong to, teammates' shared agents (`Name@Workspace`; see the Workspaces topic). The Orchestrator's allowed subagents, permissions, and limits live in Settings → Agents → Delegation; each custom agent's "Delegate to subagents" settings live in its own Subagents tab. Deleting an agent removes it from every allow-list at once.
