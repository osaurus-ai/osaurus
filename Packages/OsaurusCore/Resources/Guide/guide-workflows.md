# Workflows

A workflow is a fixed graph of steps with a typed input and a typed output. Each step is one of:

- **Inference**: one model call that must return JSON matching the step's output schema.
- **Dialog**: a form the user fills in mid-run (text, choices, files, secrets). Fields marked *remember* are saved per form and offered next time; two forms that ask for the same key keep separate answers. A form waits for you as long as you take: time spent on a form, a folder card, or an approval never counts toward a step's timeout. A form only gives up if its workflow sets `expires_after` (for runs nobody may be watching). If a form closes before you send it, what you typed comes back the next time it is asked, until Osaurus quits; secret fields are not kept.
- **Code**: a short JavaScript function that runs in a sandboxed helper with a time and memory limit, no network, and no file access. It reads its input, `ctx.run` (`id`, `workspace`), and `ctx.caller` (`kind`, `agent_id`, `agent_name`, and `channel` when a channel message started the run). A code step may be **Python** instead (`def run(input, ctx)`): it runs through the workflow's own sandbox environment (see Dependencies), where the pip packages the workflow declares are installed, and whatever it prints goes to the step's log. A Python step runs under its time limit (it is stopped when the limit passes) and a memory cap (2 GB of address space unless the step sets `memory_limit_mb`); it reaches only the hosts in its `network` list (none when the list is empty), and its declared secrets reach it in memory, never as a file in the run workspace, with their values hidden from its log.
- **Tool**: calls one tool with fixed or bound arguments, without a model. Any tool an agent can call works here (built-in tools such as `file_write` or `shell_run`, MCP tools, plugin tools), and its result becomes the step's output: a tool that returns JSON passes it through, and plain text comes back as `{ "text": … }`. A failed call fails the step (and retries if the step allows it).
- **HTTP**: one web request described without code: method, URL, query parameters, headers, body, and how it authenticates (a connection you signed in to, a bearer token, basic auth, a header, or a query parameter, each from a declared secret). It only reaches the hosts the step names, over https (http for localhost), never a private or link-local address and never Osaurus's own server port, and every redirect is checked against the same rules. Its output is `{status, ok, headers, body}`; a non-2xx status fails the step unless the step says otherwise. A step that reads a paged list can follow the pages itself (a cursor, a next-page URL, the `Link` header, or page numbers) up to a cap of at most 100 pages and hands the next step one merged list as `body`, with `pages` and `complete` (false when the cap stopped it short).
- **Wait**: pauses the run for a number of seconds or until a moment (up to 30 days), then goes on. A run keeps waiting across a relaunch of Osaurus; a test run in the Architect skips the wait and says so in the log.
- **Map**: runs one step once for each item of a list, several at a time (4 by default, up to 16), and collects the results in order as `{items, count, failed}`. Inside the step, `{{item}}` and `{{index}}` name the current item and its position. One failed item fails the step, or, when the step says so, is left null and listed under `failed`.
- **Workflow**: runs another installed workflow as one step. The step's input is that workflow's input and its result is the step's output. It runs as its own run (in that workflow's history, with its own forms and files) on behalf of whoever started the outer run. A workflow cannot call itself, directly or through others, and nesting is bounded. The other workflow keeps its own setup: its models and keys are bound there, not on the workflow that calls it, and a step cannot run until that workflow is installed and set up on this Mac (its setup problems show under the calling workflow's **Before It Runs**). What it reaches — hosts, tools, MCP servers — is counted on the calling workflow's import review and its page, followed through further workflow steps.
- **Agent**: hands a task to another agent and waits for its answer. The agent is one of your custom agents, named as the template names it, or a teammate's **shared agent** (see the Workspaces topic), which runs on its owner's Mac with their model, tools, and workspace credits and sees only the task text. The task may bind earlier outputs like any text field. The step's output is `{text, agent, session_id, needs_input}`: the agent's final answer, who answered, its session, and whether it ended asking for more (`NEEDS INPUT:`). Files the agent shared with `share_artifact` join the run's **Files** (from a shared agent, at most 16 files and 4 MB in total). It runs on the agent's own model, not a model slot, for up to an hour by default. Before it runs, the step asks the same way the Orchestrator does: the starting agent's subagent **Permission** for your agents (Always Allow by default) and **Permission for shared (workspace) agents** for a teammate's (Ask by default; the card says the task goes to their Mac). A run nobody is watching (a schedule, an automation, an API call) cannot be asked, so it stops at that step and names the setting to change. A shared agent that is offline, unshared, or in a workspace you left fails the step before anything is sent. An agent step cannot run inside a **Map** (give the agent the whole list in one step) or inside a run that is itself an agent's delegated task. **Edit Step…** picks the agent from **On This Mac** and **Shared in *workspace*** and edits the **Task**.
- **State**: the workflow's own stored data, kept between runs as named tables of key → value (default table `vars`). Actions: `get` (`{exists, value, updated_at}`), `set`, `increment` (by 1 or by a number; the value must be a number), `delete`, `list` (newest first, up to 1000 rows), and `clear`. Table, key, and value may be bindings. This is how a workflow skips items it has already handled, keeps a counter, or caches a lookup without a file or an agent's memory. Values are at most 64 KB and a table holds at most 5,000 rows. An installed workflow's runs share one store; the Architect's test runs use the draft's own. Review or clear the tables under **Stored Data** on the workflow's page; uninstalling the workflow removes them.
- **Decide**: picks which edge the run follows next.
- **Agentic**: a bounded tool loop over the tools the step lists (built-in, MCP, or plugin), ending in one structured answer. Its `max_steps` is 1 to 12 (default 8); the step runs at most that many tool calls, and a larger value fails validation rather than being quietly cut down.
- **Reply**: posts a message into the channel conversation that started the run (Slack, Discord, Telegram, iMessage, WhatsApp, email, n8n …), and optionally a file from the run's workspace or one of its folders, with a caption. Text, file, and caption may be bindings. Use it to acknowledge a request early ("On it…"), to report progress between long steps, or to send the result as a file. Its output is `{sent, platform, room_id, thread_id, attachment_sent, truncated, reason}`; `truncated` is true when the text was longer than the channel takes and was cut short. A run nobody started from a channel (a tab, a schedule, an agent's tool call, the Architect's test) does not fail: the step outputs `sent: false` with `reason: no_conversation` (`test_run` in a test, which logs what it would have sent). Files go out on iMessage and WhatsApp; elsewhere the text is sent and `reason` says the file was not (`unsupported_on_<platform>`, or `no_live_connection` when the run resumed after a relaunch on a channel that only takes files as a reply to the message). A step inside a **Workflow** step replies in the outer run's conversation. A run posts at most 20 replies (its inner workflows count toward it); past that a Reply step sends nothing, outputs `reason: reply_cap` and the run goes on — a Reply inside a **Map** is flagged for this, so reply once after the map instead. Replies go through the same send checks as every channel post: **Pause All Sending** stops them (`reason: writes_paused`, the run goes on), and on iMessage a file must be in a folder the channel allows. If Osaurus quits mid-run, the run picks up at the next launch and its replies, open form questions and the rule's final post still reach the conversation, through the channel's connection.
- **Media**: makes images with an image model on this Mac — **Image** (from a prompt), **Edit** (one to four source images changed by a prompt), **Upscale** (one image, 2× or 4×) — or a **Video** with a local Wan model on this Mac or a connected provider. The step names a model family (such as Qwen-Image 2.1, so every Mac uses its own copy), one exact model, or your default image model, and where it may run (**This Mac**, **Provider**, or **Either**). It takes every setting the model has: prompt, negative prompt, size, steps, guidance, edit strength, seed, how many images (up to 8, made in one job with a seed each), batch size (for a model that makes several images at once), the sampler, scheduler, and shift the model lists, a live preview every N steps, format, upscale factor, and for video the duration, resolution, aspect ratio, and audio; a local video also takes its size, steps, guidance, **Frames** (4n+1), and **Frame Rate**, and the frames must equal the duration times the frame rate (49 frames at 16 fps is 3.0625 seconds), so either the duration or the frames and frame rate is enough. Any of them can be typed in the step or taken from the run with the link button (`{{input.seed}}`, a map's `{{item}}`). **Seed** is **Random** (a new one each run), **Fixed** (the same one, to compare prompt changes), or **Step Through** (the seed plus the item number inside a **Map**, for a seed sweep). Source images come from an earlier media step (`{{nodes.gen.output.images}}`, or one of them as `{{nodes.gen.output.images.0.path}}`) or a file in the form, so a workflow can generate, then edit, then upscale. Its output is `{images: [{path, url, seed, width, height, format}], videos, model, backend, count}`, and the files join the run's **Files** on their own with the settings that made them. Local steps, local video included, run without asking once the workflow is installed and cost nothing; a provider image or video is billed, so it asks for approval on each run and shows the price first. A run nobody is watching (a schedule, a folder or channel automation, an API call) cannot be asked, so a billed media step there fails and says so unless the agent's **Image** or **Video** permission is **Always Allow**. Local image jobs from every workflow run take turns on this Mac, and a **Map** over a media step runs its items one at a time whatever its concurrency says, so the chat model is unloaded and restored once per job rather than over and over. **Edit Step…** shows only the fields the chosen model uses, with its limits (for example sizes in steps of 32 up to 2048, which the draft check also flags), warns when a linked field names an input the workflow does not have, and says when no model on this Mac can do the step; setup lists a missing image model as a blocking item. A media step may run for up to 30 minutes, since a model's first load is slow. Stopping a run stops a queued or loading job at once; an image, upscale, or local video already on the GPU stops at the model's next step. When Server → **Memory Safety** is **Strict** and a job's estimated peak memory is over its budget, the step fails before the chat model is unloaded and names the setting, the estimate, and the budget; the other modes let the job run. When a batch fails partway, the images it finished are kept in the run's folder and the error lists them. When the model reports what it ran, the image's settings and its `effective_parameters` show that (Qwen-Image 2.1 Turbo always runs its fixed 8-step schedule) and keep any value the step asked for differently as `requested_*` (a local video's `effective_parameters` list its size, frames, frame rate, steps, guidance, and seed); the step fails before the model loads when a value is outside the model's limits, such as a sampler the model does not list, naming the field. A provider step does not take the sampler, scheduler, shift, batch size, preview, or frame settings, and its log says which were not sent.

Any step can be switched to **Bypass This Step** in **Edit Step…**: it does not run and hands its input on (an Edit or Upscale hands its source images on as its images), so the rest of the chain still runs while you work on one part. What it hands on must still fit the step's output schema, since later steps were built against it; a bypassed step whose input does not fit fails with that reason. A bypassed step is dimmed and crossed out in the graph, and the draft warns about it so it is not saved that way by accident. Templates that use media or bypassed steps are written as format 3, templates with agent steps as format 4, and templates whose tool steps run as a named agent as format 5, so an older Osaurus asks to be updated instead of failing to read them.

Tool and Agentic steps cannot use workflow tools (`workflow_<name>`, `run_workflow`); composing workflows is what the **Workflow** step is for. Nor can they use tools that only make sense in a live chat (agent hand-offs, sandbox setup, chat-only capability tools); handing work to an agent is what the **Agent** step is for. Steps can bind `{{run.id}}`, `{{run.workspace}}`, `{{caller.kind}}`, `{{caller.agent_id}}`, `{{caller.agent_name}}`, `{{caller.channel.platform}}`, `{{caller.channel.room_id}}`, `{{caller.channel.thread_id}}`, `{{caller.channel.sender_id}}`, `{{caller.channel.sender_name}}`, `{{caller.channel.room_name}}` (empty when no channel message started the run), and `{{folders.<key>}}` (a declared folder, see Folders) alongside `{{input.x}}` and `{{nodes.<id>.output.x}}`.

### Branches, failures, and merges

- An edge may carry a condition on the previous step's output: equals, not equals, in, exists, empty, true/false, greater or less than (numbers, numeric strings, and dates), contains, starts with, ends with, or matches a regular expression; conditions combine with *all*, *any*, and *not*. A step runs when one incoming edge carries (*join: any*, the default) or, for a merge after parallel branches, only when every incoming edge does (*join: all*). A step no edge reaches is skipped and binds as null.
- Each step says what happens when it fails for good (after its retries): **fail** stops the run (the default); **continue** marks the step failed, binds its output as `{error: {message, kind, retryable, fix_in, attempts}}`, and lets the run go on; **skip** treats it as a branch not taken. An edge marked **on: error** carries only when its step failed and continued, so a workflow can take a fallback path or notify someone instead of stopping; **on: always** carries either way.
- A failed run says what went wrong and, on the line under the error, what to change: the step itself, a setup item (a secret, connection, folder, program, or model slot), an app setting (named with its place in Settings, for example **Server → Memory Safety** or **Agents → Delegation → Local Models & Memory → Swap Local Models for Subagents**), or nothing yet because another attempt may pass.
- A failed run's page (under its **Steps**), and its **…** menu in a Runs list, have **Retry from Failed Step**: a new run that keeps the results of every step that had finished, runs the failed step and everything after it again, and works in the same scratch workspace so files earlier steps wrote are still there. The new run shows which run it continues. A run of a workflow that has changed since, or that needs setup, cannot be retried this way; start a new run instead.
- **Fix with the Architect** (on the same card and menu, on a failed run in the workflow's **Recent Runs**, and on a failed test in the Architect's **Test** tab) opens the workflow in an Architect chat that already holds the failed run: the Architect reads the run's steps, outputs, logs, tool calls, the failed step's definition, and where the fix belongs (`workflow_runs`), can check whether the same failure repeats across runs, changes the step, re-tests from the failed step with that run's input and the finished steps' real outputs pinned (`workflow_test` with `from_run`), and proposes the fix as the next version. When an app setting or a setup item stopped the step, it tells you what to change instead of editing the workflow around it. Saving is still your click.
- **Models.** A step that uses a model names a model slot, and the slot either **requires** a model (the workflow runs only on that model; setup asks you to install or connect it, and another model cannot be picked) or **suggests** one (setup preselects it and you may pick another that can do the job). A required slot shows **Required model** in setup, and a slot whose step uses tools only takes a model that can call tools. The Architect picks from the models on this Mac and your connected providers, and tests run on the slot's model; a test that ran on another model than the one a slot requires does not count toward saving.
- **Fix repeated failures automatically** (in the workflow's details under **Who Can Start It**, off by default) does the same without being asked: when the same step fails the same way three runs in a row, the Architect drafts a fix in a background chat and a notification offers it for review. One recurring failure gets one draft; nothing is saved until you review the Save card in that chat.

A step's instructions are the author's; what earlier steps produced (web pages, email bodies, tool results) is not. When a Generate, Decide, or Agentic step references `{{nodes.<id>.output…}}` in its instructions, the value does not go into the model's system prompt: a `[[ref:N]]` placeholder stands in for it there, and the content itself travels in the user message inside an `<untrusted_content>` wrapper, so the model treats it as data to work on rather than as instructions. The same applies to `{{input…}}` when an agent or the Orchestrator started the run; input a person typed in a tab or test renders inline. `{{run…}}`, `{{caller…}}`, and `{{folders…}}` always render inline, except `{{caller.channel…}}`: the sender of the message chose those values, so they travel as data like a step's output.

The tools a workflow's steps call belong to the workflow: installing it lets those steps call them for whoever runs it, even an agent that does not have the tool turned on. Each tool's own permission still applies: a tool set to ask shows its approval card during the run, quoting the step's intent (or its name) as the reason, and **Don't ask again** → **For the Rest of This Run** covers that tool for the rest of the run. While the card waits for you the step shows as waiting and its time limit stands still, so reading or looking something up never times the step out. File and shell tools work in the calling agent's working folder when it has one, otherwise in the run's own workspace folder.

Steps that drive the browser or the Mac (`browser_use`, `computer_use`, `applescript`, `mac_query`) or generate media (`image`, `video`) need no agent toggle either: the workflow's step is what allows them, whoever starts the run (a tab, a test, the Orchestrator, or an agent). They run on the calling agent's model and browser session, or the Default agent's when there is none, and Browser Use and Computer Use still confirm risky actions as they go. What setup cannot switch on by itself shows as a setup item: a macOS permission such as Accessibility in the **Permissions** step, a missing AppleScript, image, or video model, or no default chat model in the **Tools** step. The **Tools** step marks these tools **Confirms actions as it works**.

### Dependencies

A workflow whose shell steps need a program your Mac may not have (`yt-dlp`, `ffmpeg`, `pandoc`, a command-line tool from PyPI or npm) declares it as a **dependency**: a package manager (`pip`, `npm`, or `apk`), the packages, and the commands they provide. Dependencies are part of the template, so they travel with it. The Architect declares them for you when a step needs one; it never puts an install command in a step or asks you to install something in Terminal.

- A workflow with dependencies, a Python code step, or any step that runs shell commands (a `shell_run` Tool step, or an Agentic step that may call `shell_run`) runs its shell and Python steps in a **sandbox environment of its own** (the Sandbox from Settings → Sandbox, with a separate Linux user, Python environment, and npm workspace per workflow), never on your Mac directly. Such a workflow needs the Sandbox set up, and its shell steps work in the run workspace, not in your folders. They run Linux programs, not the Mac's own (`qlmanage`, `sips`, `osascript`): the Architect picks a Linux program and declares it, and a draft whose shell step calls a macOS program, names a folder on your Mac, or passes a picked or declared folder to its command cannot be tested until the step is fixed. Setup installs the packages there once, checks that each promised command exists, and every run reuses them. The run's workspace folder is shared between your Mac and the sandbox, so file steps (`file_write`, `file_copy`) and shell steps see the same files.
- The setup wizard gains a **Dependencies** step: each package with **Installed**, **Not installed**, **Needs reinstall** (after the sandbox was reset), **Reinstalls on next run** (an `apk` package the sandbox removed to make room for other agents and workflows; the next run installs it again by itself), or **Unavailable here** (`apk` packages need the Linux sandbox of macOS 26+; `pip` and `npm` work everywhere). **Install** starts the sandbox if needed and shows the installer's progress; **Check Again** re-reads the state. A missing dependency is a blocking item, like a missing model: the workflow reads **Needs setup** until it is installed, and a test run in the Architect opens **Set Up Test Run** on it. If the Sandbox is not provisioned yet, the step says so and **Open Sandbox** takes you there; a sandbox with network set to **none** cannot download packages.
- The sandbox cannot see your folders. To work on your files, the workflow copies them from the folder you picked into the run workspace first (`file_search`, then `file_copy` for each file), and the shell step works on those copies. To hand a file back, the workflow asks you for a folder (a form field or dialog field of type *folder*, or a declared folder) and copies the result there with `file_copy`; the run may write only into the folders and files you picked, the workflow's declared folders, and its own workspace. Files up to 4 GB can be copied out of a run this way.
- A shell step whose program is missing fails with the shell's message (exit 127) rather than passing empty output downstream, and names the fix: declare the program as a dependency.
- Uninstalling the workflow removes its environment. **Reset** or **Remove** in Settings → Sandbox clears every workflow's installed packages; each such workflow asks to install them again.

### Folders

A step's file tools may use the folder of the chat or agent that runs it, the run's own workspace, folders and files you pick in the run's form, and the workflow's **declared folders**. Anything else is outside the run.

- A workflow that always reads from or saves to the same place (an invoices folder, where downloads go) declares that folder by name. The Architect does this for you instead of writing a path from its Mac into a step. Steps name it as `{{folders.<key>}}`.
- The setup wizard gains a **Folders** step: each declared folder with what the steps do there (**Reads files** or **Saves files**) and **Choose…** to pick the folder on this Mac. An unchosen folder, or one that no longer exists, is a blocking item. Templates carry only the folder's name and a suggestion, never your path.
- Inside those places, a step saves only where the workflow's definition says (its **Your files** card): a folder you pick that it only reads stays read-only, and one it saves into a subfolder of (`{{input.folder}}/png/…`) takes saves only in that subfolder. The run's workspace is always writable.
- If a step still reaches a folder outside the run, or saves somewhere the workflow doesn't say, the run waits on a card: **Allow** *workflow* **to read** *folder*? (it can't save or change anything there) or **Allow** *workflow* **to save in** *folder*?, with **Allow for this run**, **Always allow**, or **Don't allow**. The card shows wherever the workflow's forms show (the chat, the run page in Workflows, or a notification). **Always allow** saves the folder with the installed workflow (or the Architect draft), as read-only or for saving, matching the card; a run started by a schedule, a watcher, or an outside client can't show the card, so the step fails and names the folders it may use.
- Before a step replaces or changes a file that's already on your Mac (outside the run's workspace), the run asks once per folder: **Replace files in** *folder*? with the same three choices. **Don't allow** stops the step (nothing is replaced); a run nobody can answer for fails the same way. Workflow file steps don't delete files on your Mac; a workflow that calls `file_undo`, which can take back a file it created, names it under **Also uses**.
- The workflow's details list its chosen folders and every always-allowed folder under **Before It Runs** (**Always allowed to save**, **Always allowed to read**, **Always allowed to replace files**); **Remove** takes one back. **Change…** picks a different folder for a declared one.

### Files

A run can hand you files: the ones its result names as files (the saved invoice PDF, the downloaded video) and any a step shares with `share_artifact`. They show under **Files** in the run's result, on the run page in Workflows and in the Architect's test result, each with its type and size, **Open**, and **Show in Finder** (double-click opens it too). A file the result names that is missing, or that lies outside the run's folders, shows why instead. A shared file is copied into the run's own files, so it stays even if the step's workspace changes; uninstalling the workflow deletes them with its runs.

Images and videos show as a grid above the other files. Clicking one opens it large, with zoom and pan for an image and a player for a video; the left and right arrow keys step through the run's media, and the bar under it lists the settings that made it (prompt, model, size, seed, steps, guidance) with **Save As…**, **Copy Image**, **Open**, **Show in Finder**, and **Copy Settings as a Media Step**, which puts a media step that makes the same image again (seed fixed) on the clipboard to paste into a draft or hand to the Architect. **Save All…** copies every image to a folder you pick. PNG files keep their settings inside the file too, so they survive being moved. While a media step runs, its row shows a progress bar with the step it is on and the time left, and, when the step sets a preview interval, a small preview of the image as it forms (previews are not kept with the run). In the Architect's graph, each media step shows the last image it made in a test, and the lines that carry images or video between steps are colored, with a legend.

When an agent or the Orchestrator runs the workflow from a chat, the same files appear as attachments on that chat's reply, and the agent is told you already have them. Runs started by an outside client (HTTP, MCP) return only the paths.

Workflows are shared as **templates**: versioned, portable files that carry the graph, its schemas, and what it needs to run (model slots, secrets, MCP servers, plugins, tools, permissions). Installing a template makes an **installed workflow** on this Mac. Each template installs once per Mac, and saved answers are shared across every caller.

## Getting started

The everyday home for workflows is **Workflows** in the chat window's navigation rail, on its left edge, under Chat.

- The header names the agent and counts its workflows. The list shows the workflows this chat's agent can run, each marked with its summary, **Needs setup**, or **Running…**. For a custom agent those are the workflows turned on in Settings → Agents → (agent) → Abilities → **Workflows**; for the Orchestrator, the workflows marked **Osaurus can run this for you**. Both change from here too.
- **+** in the header adds a workflow: pick one already **On This Mac** to add it to this agent at once, or a **Starter** to preview it first. **Manage Workflows…** opens Main window → Workflows.
- A row's **…** menu (or right-click) has **Open** and **Remove from (agent)**. Removing only takes it off this agent's list; the workflow stays installed.
- Click a workflow to open its form in a new tab of this window, run by the same agent: your chat, its tab, and the sidebar stay as they were.
- **Starters** lists the built-in workflows you have not added yet: **Social Post Writer**, **Meeting Action Items**, and **Email Reply**. Clicking one opens a preview: the form you will fill in (with its example), the steps, what you get back, and anything to set up first. **Add Workflow** adds it right away when nothing needs setting up (otherwise the setup wizard opens first), adds it to this chat's agent, and opens its tab with the example filled in. Starters prefer Apple Foundation Models and fall back to your default model.
- Past runs of a workflow are in Main window → Workflows: click its row for the last five, or **See all runs** for its page (**Runs**, and **All Tasks** for the full list in Tasks → History, filtered to it). Click a run to open its run page. Architect test runs stay in the draft's **Test** tab.
- When the agent has no workflows yet, the lens says so and points to **+**. To make your own, start a chat with **Architect** (it is in the Agents list). In the Architect's chats the Workflows lens lists every workflow on this Mac to edit, and the draft has its own **Draft** lens.

Main window → Workflows is one page. Its header has **Import** and **New Workflow** (⌘N), and under the title, once anything is published, a quiet line shows how many are published, their total installs, and **Your author page** on store.osaurus.ai, next to **Connections** and **Automations** links. **Running now** shows every run in progress, whoever started it (you, an agent, or an automation, marked with a bolt and its name), with its steps filling in, **Stop**, and **Respond** when it waits on a form. Below it the workflows sit in tabs: **All** (every installed workflow), **Drafts** while any are unfinished (each with where it stands: Design → Test → Save → Publish, and **Continue**), **Published** once anything is, and **Workspaces** while you belong to a workspace (see **Workspace** under Installing and setup). The page opens on the tab you used last. On All and Published, a **Search by name or tag…** field sits in the tab row and one chip per tag sits above the list. Each row shows an **Update to vN** chip when one is available, a **Live** badge once published (with who can see it and how many installed it; it opens the published dashboard), **Shared in *workspace*** when you installed it from a workspace, when it last ran, and **Run** (**Set Up** while it needs setup). Run starts at once when the workflow needs nothing, otherwise a sheet asks for its input; either way the row opens and the new run fills in there. Clicking a row shows its last runs, **See all runs**, **Run with different input**, and the automations that start it. Every row's **…** menu has **Save as File…** and **Publish…** (**Manage Published…** once live). **New Workflow** opens its own page (‹ Workflows in the title bar goes back): the Architect's composer, ready to type in, then **Or add a ready-made workflow** (each opens a preview with **Add**) and **Import a Workflow**. With no workflows and no drafts, that page is all Workflows shows, titled **Create your first workflow**. **Import** (or dropping a file anywhere on Workflows, or **Install workflow** on a store.osaurus.ai page) brings one in. The Architect's model, name, avatar, and permissions are in Settings → Architect.

## Architect

The Architect is a built-in agent that designs workflows. Pick it in the sidebar's Agents list, open it from a workflow's **Edit with the Architect** (a workflow's **…** menu in Main window → Workflows, **Edit** in the footer of a workflow's page, or **Continue** on a draft in Workflows → **Drafts**), or ask the Orchestrator to hand off ("build me a workflow that…"). Its empty chat offers starting points (social posts, meeting notes, email replies, or something else).
- **Editing a saved workflow**: in an Architect chat, open the inspector's **Workflows** lens and click the workflow (or **+** for a new one). The Architect's chat opens on it, the inspector switches to its **Draft** lens holding the workflow as saved (the row stays highlighted under **Workflows**); the empty chat offers edits (change what it asks for, change what it gives back, run it on another model). A workflow built or edited in an earlier Architect chat opens that chat, with its history; when the workflow has a newer saved version than that chat last saw, its draft is brought up to it (Undo restores the old one) and the Architect is told. A workflow no saved Architect chat has touched starts a new one. A blank Architect chat is reused for the pick.
- A new Architect chat in Workflows opens on a guided start, without the draft half: **What should this workflow do?**, Design → Test → Save → Publish, ideas to start from (each puts a sentence in the message box to finish), and **Change a saved workflow instead**, which opens Workflows. The draft half appears once you send. Until the Architect has drafted a step, it shows the shape of the steps to come. A draft that has steps but no conversation yet (a saved workflow opened for changes) opens with **What should change in …?** and ways to begin; in a window too narrow for both halves, it opens on the draft.
- While the draft edits a saved workflow, its header reads **Editing v2** (with the saved workflow's name once the draft is renamed), and saving makes that workflow's next version. To build something different from it instead, choose **Save as New Workflow** in the draft's **…** menu: the draft then saves as a new workflow and the saved one stays as it is, and its row in the lens is no longer highlighted. The Architect does the same when you ask it for a different workflow in that chat. The save prompt names the saved workflow when the draft would replace it under a new name.

- Before building, the Architect asks at most three short questions, only about what your description leaves open (what you fill in, what you get back, and for private material whether it must stay on this Mac). It then states the plan as a short list of steps and builds it.
- **Starting from what exists**: for a common job the Architect searches the store registry (store.osaurus.ai) and your own library first and, when one fits, adopts it into the draft and adapts it instead of building from scratch (the draft stops editing any saved workflow it was opened from). To connect to another service it searches the Osaurus MCP Directory and tells you which servers are already connected, or reads the service's OpenAPI (Swagger) description and builds **HTTP** steps from it. When the service has no OpenAPI file, it asks you for one or works from the API description you paste into the chat. It only fetches https files, up to 2 MB each.
- **Sign-ins**: a step that needs an account rather than a key declares its secret as an OAuth sign-in. Setup then shows **Sign in to <service>**; the browser opens, you approve, and the step reads a live access token (Osaurus renews it when the service issues expiring tokens). When the service requires you to create an OAuth app (Slack, GitHub, Google, Notion, and the rest of the catalog), the Secrets step shows **Sign in with your own <service> app**: the steps for that service, a link to its developer settings, the **Redirect URL** to register (always `http://127.0.0.1:47823/callback`, with a copy button), and the **Client ID** and **Client secret** fields. While it waits for the browser, **Cancel** stops the sign-in so you can fix the app's redirect URL and try again; a service that shows a redirect URL error never returns to Osaurus on its own. Another app using port 47823 blocks sign-ins until it lets go. **Or paste a token instead** takes a token you copied from the service when it offers one.
- In the Architect's chats the inspector's lenses are **Draft** and **Workflows** (Draft takes File Changes' place), and the Architect opens on Draft at the inspector's full height. With no draft yet it offers **Change a Saved Workflow…**, which opens Workflows. Its header is the name, a title you click to rename, and the **…** menu; under it **Design → Test → Save → Publish** marks where the draft stands with its status beside it, then **Editing vN** when it edits a saved workflow and the full summary, then the **Design** and **Test** tabs. The status reads Drafting, a count of things to set up, Ready to test, Testing…, Tested (the latest test passed and the steps haven't changed since; a rename or summary edit keeps it), or Test failed. The **…** menu has Undo (named for the steps the last change touched, such as "Undo the Architect's Change to Flag anomalies"), **Set Up…**, and, while it edits a saved workflow, **Save as New Workflow**.
- Both tabs are sections in one scrolling column, like an inspector: click a section's header to open or close it; the others stay as they are. Each header says what is inside ("3 steps · needs attention", the fields you fill in, the first line of a result). A test's steps and its result stay at most about 60% of the panel tall; anything longer scrolls inside its own box.
- **Design** shows the draft in plain words in **Steps**, **You fill in**, **You get**, **Your files**, and **It uses**; **It uses** and **Changes** start closed with a one-line summary ("2 secrets · 3 tools"), and any section closes or opens on a click. **Steps** stays at most about 60% of the panel tall and scrolls inside past that. **It uses** is a read-only list of the secrets, tools, MCP servers, plugins, packages, folders, and hosts the workflow needs; you enter secrets and choose folders in **Set Up…**. **Before it can be tested**, at the top of Steps, is the one list of what is still missing, with **Set Up…** when this Mac needs something; until that is done, **Set Up…** also takes the place of **Test Run** in the footer. **Steps** are cards in run order, each with what it does, the model it runs on, and **step badges**: where it runs (**Your Mac** when it reads or saves files outside the run's workspace or acts on the Mac; **Sandbox · Runs commands** for shell steps), the hosts it reaches, the secrets it reads, files it writes, browser use, whether its model runs on this Mac or in the cloud, whether it asks you or waits, and the time and tokens past test runs took (orange when it reaches outside this Mac, writes files, or runs commands in the sandbox; red when it runs commands on your Mac, drives the browser, or controls the Mac); a step that picks a path lists each branch ("If urgent → Draft reply"). A line joins each step's number to the next, green past the steps the latest test finished, and a step the Architect's latest edit changed reads **Changed**. Click a card to open it: **Runs on** changes its model right there, and a glance at its instructions sits under it. The model menu greys out models that can't run the step, grouped by why (for example "Can't return typed results" for a local model whose tokenizer can't drive constrained decoding). **Edit Step…** opens the full editor (name, instructions, and under **Advanced** the slot id and **Edit as JSON**; **Save** applies). The card's **…** menu has **Ask the Architect** (starts a message about the step in the chat), **Test From This Step**, **Bypass This Step**, and **Delete Step**. **Show Graph** swaps the cards for the graph; click a step in it to open the same summary. **Open Full View** (the arrows beside **Show Graph**) opens the draft in the full view (see **The full view** below), following the latest test as it runs; a step selected there is selected in Steps too, and its details pane has **Edit Step…** and the same **…** menu. **You fill in** lists the form's fields (**Preview Form** shows the real form with the example), **You get** lists the result fields, **Your files** says what the workflow **Reads**, **Writes**, and **Deletes** on your Mac (plus **Replaces** and **Also uses** when they apply), read from its steps, with **Your Mac** and **Sandbox** for where the work happens and the sentence the Architect says before you save. Runs hold to it: file steps save only in the folders and subfolders it names (a save anywhere else asks first), a folder it only reads stays read-only, and replacing a file that's already on your Mac asks **Allow for this run**, **Always allow**, or **Don't allow** the first time. **It uses** lists secrets, MCP servers, plugins, the tools its steps call (with whether each runs without asking, asks first, or is missing), and network hosts. In **Edit Step…**, a Tool step picks its tool from **Choose a tool** (grouped by where it comes from) and takes its **Arguments** as JSON with bindings (an argument may also be a literal `true`/`false`, number, or `null`). **Changes** (closed until you open it) lists every edit to the draft, newest first: who made it (the Architect or you), the Architect's one-sentence reason, and each change in plain words ("Added step Flag anomalies", "Renamed to …"); **Undo** on the newest takes it back.
- **Test** has **Input** (the form, prefilled with the example or with the latest test's input; **Fill with Example** switches examples), then for the test on screen, in a run page's order, its **Result** once it has one and its steps (titled **Testing…**, **Test failed**, or **Test stopped** until there is a result, with a progress bar while it runs), each opening to its details, and **Earlier tests**, where clicking one shows it and **Use This Input** in its context menu fills the form from it. Starting a test opens its steps and scrolls to them; when it finishes its result does the same. Once a test has run, Input starts closed, and Earlier tests is closed until you open it.
- The footer's main button is always the next step: **Set Up…** while the draft needs setup, **Test Run** until a test passes, then **Save…** with **Test Again** beside it; **Stop** takes its place while a test runs, and a line beside it says what comes next. **Save…** asks what changed in this version, saves without waiting for the Architect, and then offers **Try It**. Both the footer's save and the Architect's save card show the **test evidence**: each test run since the steps last changed, with the example it used, pass or fail, how long it took, the step that failed, and a glimpse of the result. When the steps changed, **Save** waits until one test has passed (the Architect's `workflow_propose_save` is refused the same way, with the evidence); when only the name or summary changed, no test is needed.
- The Architect has its own step budget (at least 80 tool calls per message, more if Max Tool Attempts is set higher). If a large build still runs out, it says so and offers **Continue**, which picks up from the saved draft.
- A test run first checks setup. When a model slot, secret, MCP server, or dependency is missing, the draft opens **Set Up Test Run** instead of running; **Set Up…** in the draft opens it too. What you enter there stays with the draft. When the workflow takes a folder or file you pick on its form and the Architect's test does not name one, the chat shows **Choose what to test with** with the same picker as the form; later tests reuse that choice, and closing the card runs nothing. The Architect never asks you to type a path. Answers given to a test run's forms stay with the draft too: they never become an installed workflow's saved answers and are removed when the draft is deleted.
- The Architect can design on Claude Code or Pi instead: pick the runtime's column in the Architect chat's model picker. It keeps its instructions and gets only its workflow tools, through the Osaurus server (which must be running), and none of the harness's file, shell, or web tools. The draft panel, test-run forms, and the Save card work as usual. A permission set to ask first refuses on a harness, because nobody can approve inside it.
- **Architect Model** (Settings → Architect → Model) picks the model it designs with. It needs tool calling, so small-context models that run with tools off (such as Apple Foundation Models) are not offered, and a warning shows when the default model is one.
- Settings → Architect also holds its **Name**, **Avatar** (upload your own image or pick a dino), **Extra Instructions** (added to its built-in instructions, never replacing them), and **Permissions**: whether it asks first, runs without asking, or never runs **Edit the Draft** and **Run Test Workflows**. Both run without asking by default. If you set one to ask first, the approval card offers **Run once** and **Deny**, with **For the Rest of This Reply** and **Always Allow…** under **Don't ask again**. Saving a workflow always asks you.
- When the draft is ready it proposes saving it as a template; you confirm before anything is installed (or use **Save…** in the draft at any time). When you asked for the workflow to run on its own ("every weekday at 8", "when a webhook is called", "when a file lands in Downloads"), the save card also shows **Then run it** with the trigger and a checkbox (on by default): **Save** installs the workflow and creates that automation in one tap, and saving again does not add a second one. A webhook trigger's URL and secret are then in Settings → Automations. After **Save**, **Try It** opens the new workflow's tab with the test example filled in. The saved workflow appears in the Workflows lens of the Orchestrator and of any agent you add it to.

## Installing and setup

- **Import** (Main window → Workflows header) picks a `.osaurustemplate` file; dropping one anywhere on the screen, double-clicking one in Finder, or clicking **Install workflow** on a store.osaurus.ai page (an `osaurus://templates-import?url=…` link) does the same. Links are accepted only for template files on the store registry (`api.store.osaurus.ai`); a link to any other address is refused with "Osaurus installs template links from store.osaurus.ai only." Nothing installs from a link without the same review. A file of the other kind (an agent template dropped on Workflows, or a workflow on Agents → Templates) opens on its own page, and so does a link: an agent template's **Install agent** button opens the import on Agents → Templates. The import review shows code, network allowlists, cloud model slots, secrets, **Tools its steps call** (each tool, the steps that call it, and its permission here), **Installs packages in its own sandbox** when the template declares dependencies, **How to connect its MCP servers** when the file says, and whether the signature matches; an edited template reads as unsigned. Importing a higher version offers an update; the same version with different content offers keep both or replace. A file opened from a link shows the host it was downloaded from and always goes through setup after import; it is never added and callable in one step.
- **Import and Add** saves the file and adds the workflow in one step. When this Mac already has everything it needs, it is added right away and a toast offers **Run**. Otherwise setup opens on what is missing. A newer version of an installed workflow opens its update.
- **Share…** on a workflow's page (or **Publish…** and **Save as File…** in its row's **…** menu) asks how: **Save as a file** or **Publish to store.osaurus.ai**. The Architect's **Saved** card offers the same **Share…** next to **Try It**, opening Workflows on it. **Save as a file** (also **Save as File…** in a card's **…** menu) offers **Suggest the models I use** (fills slots the template leaves open with the models this workflow runs on here), **Include how to connect my MCP servers** (server addresses or commands and the names of the headers and environment variables, never their values; anything in a URL or argument that looks like a key becomes `YOUR_KEY`), **Sign with my Osaurus ID** (the file is named with your claimed `@handle` from Identity; there is no typed author name), and the file as the receiver will review it. Adding suggestions saves the template as its next version first, and the installed workflow moves to it. The import review shows **Signed by <address>** (the sender's Osaurus ID; the `@handle` next to it is the one they claimed in Identity), and any change to the file after export reads as **Signature does not match** and cannot be imported. Once a version in your library is signed, newer versions must be signed by the same ID; a file that is not can only be imported as a copy under a new name. If signing is cancelled the file is still written, unsigned. After saving, **Show in Finder** opens the file's folder. Saved answers, secret values, bindings, run history, and absolute paths are left out. An installed workflow exports the version it runs.
- **Publish to store.osaurus.ai** (the second option in **Share**, also **Publish…** in a card's **…** menu) publishes the same signed file as a page you own. It needs an Osaurus ID (without one the sheet offers **Open Identity Settings**) and is always signed with it; one authentication prompt signs both the file and the upload. Before publishing you choose **Who can see it**: **Public** (listed and searchable on store.osaurus.ai), **Unlisted** (opens only for people with the link), **Password** (asks for a password you set, 6–128 characters; the install link carries an access token so **Install workflow** still works for someone who unlocked the page), or **Workspace** (only members of the workspaces you tick, up to 20, where you are an owner, admin, or member; see **Workspace** below). Above it, **Listing Details** sets the **Name** and **Description** the page shows (the workflow file keeps its own; **Use Original** goes back to it), **Topics** picks up to 3 of the store's topics, and **Example Runs** shows up to 6 real runs: **Add Example Runs…** lists this workflow's finished runs and Architect test runs, and each one you add has an editable title, **What leaves this Mac** (the exact input and result, with secret inputs and local paths left out), and an **Include** box under each image (images are re-encoded without location or camera details). Publishing with new example runs first asks **Share N example runs publicly?**; if any listing change doesn't save, the live sheet says **Some listing changes didn't save.** with **Try Again**, and the publish itself stands. The same model and MCP suggestions apply, and the optional name is shown on the page as the name you gave, with your **@handle** (your Osaurus ID's name, or its short address). When it's done the sheet shows **<Name> is live.**, who published it and the version and visibility, a 1200×630 **share card** (name, summary, handle, link and QR) with **Copy Image**, **Save Image…**, and **Share…** (the macOS share menu), the page link with copy and **Open Page**, a QR code, and under **Advanced details** the **Install Link**, **Template File**, and **Registry ID**. If a password didn't save the sheet says **Published as Unlisted. The password didn't save.** with **Try Again** (for Workspace: **Published as Unlisted. Sharing with the workspaces didn't go through.**). Publishing unchanged content again returns the same link. If the registry already has that version with other content, the sheet offers **Publish as Version N** and saves the workflow as that version first.
- A published workflow's card reads **Live**, and its badge, footer button, **Manage Published…** in its **…** menu, and **Manage Published…** on its page all open the **published dashboard**: the name with **Published by @handle**, a status pill (**Live · v3 · Public**, **Taken down**, or **Removed by the Osaurus team**), **Open Page**, four numbers (**Installs**, **Versions**, **Live since**, **Updated**; when the registry can't be reached it shows the last numbers it had), **Versions** (the registry's versions with changelogs; when your library is ahead, a **Publish vN** button sits on the local version, and otherwise **Your library and the page match.**), **Who can see it** (change visibility or the password, then **Save**; it asks for your Osaurus ID), **Listing Details**, **Topics**, and **Example Runs** (change, reorder with the up arrow, or remove; an example from an older version is flagged **Ran on version N**; **Save Listing** applies them without publishing a new version, **Discard Changes** undoes them), **Link** (copy, the share card actions, QR), and at the bottom **Save as File…** and **Take Down…**. Opening the dashboard refreshes the numbers with a read signed by your Osaurus ID so Unlisted and Password pages show their stats too; the cards refresh in the background without signing. The **…** menu of a published card also has **Publish Version N…** (when the workflow has changed since), **Copy Link**, **Open Page**, and **Take Down…**.
- Agent templates publish the same way from Agents → Templates (a card's **…** menu → **Publish…**); their pages live at store.osaurus.ai/a/… and carry any workflows the agent uses inside the signed file. The registry lists both kinds; its home and search pages filter **Workflows | Agents**. The Architect's registry search only returns workflows.
- **Published with an agent**: publishing an agent template (Agents → Templates) also gives its workflows that are yours their own pages, with the agent's visibility, unless you turn off **Give my workflows their own pages**. Such a workflow's dashboard says **Its page came with publishing the <Agent> agent**, and its card's button says so when you point at it. Its page on store.osaurus.ai lists the agent under **Used by agents**, and the agent's page links back with **Its own page**. Taking the agent down leaves the workflow's page up; take it down from its own dashboard or from the agent's **Workflows it brings** list.
- **Workspace**: a workflow or agent template published to a workspace is listed for its members in Main window → Workflows → **Workspaces** (one section per workspace) and in Settings… (⌘,) → Sharing → Workspaces → *workspace* → **Workflows** (**Open in Workflows** goes to the tab), not on the store, and is not reviewed. Each row reads **Install**, then **Update**, **Set Up** while setup is unfinished, or **Open**. A workspace that's suspended, or a list that couldn't load, says so instead of showing nothing; **Workspace settings** opens the workspace. Any member, viewers included, can **Install** a copy (or **Update** when a newer version is shared); it goes through the same import review and setup and then runs on their Mac with their own keys, models, and connections. The download proves membership with a short-lived workspace attestation sent only to the store registry; someone outside those workspaces gets "This template is shared with a workspace you're not a member of." The author, and the workspace's owners and admins, can remove a listing (**Remove from workspace**); copies already installed keep working. Leaving a workspace takes your listings out of it, and a suspended workspace can't install. Change which workspaces see it under **Who can see it** in the published dashboard. An agent template published to a workspace keeps its workflows bundled inside it rather than giving them their own pages. To let teammates run a workflow on *your* Mac instead of installing their own copy, see **Teammates can run this** under Running a workflow.
- **Runs on *X*'s Mac**: the Workspaces tab also lists workflows a teammate's shared agent runs for the workspace (they turned on **Teammates can run this** for it). **Add to My Workflows** adds one without a copy: it then lists under All → **On teammates' Macs** with **Run**, and each of your agents' Abilities → **Workflows** lists it with the rest. Your agents reach it the same way as an install: the Orchestrator with `run_workflow` while **Osaurus can run this for you** is on (in its row's menu), a custom agent when it's on under its Abilities. Each run goes to the owner's Mac, waits for their approval, and uses their keys, connections, and folders; a form the run stops for waits for them. Their Mac must be online and on an Osaurus that hosts workflows; an automation can't start it. **Remove from My Workflows** is in its menu. A workflow its author both shares and hosts shows both choices.
- **Take Down** takes the page down for everyone; people who installed it keep their copy. The card then reads **Taken down**, and **Publish Again** (in the dashboard or the **…** menu) brings it back at the same link. A workflow the Osaurus team removed reads **Removed** and cannot be published again from here. Installing from a published page counts once per Osaurus ID toward the page's install count: after you confirm the import (or a later update from a newer link), Osaurus sends a receipt signed with your Osaurus ID that names the workflow and version. It may ask you to authenticate once for it; without an Osaurus ID no receipt is sent, and a receipt that fails never affects the import.
- Ready-made workflows (Workflows → **New Workflow**) show what a template needs before you add it (how many steps, whether it runs on this Mac or may use the cloud, secrets to enter); **Add** opens the same preview as a Starter. **Version History** (the **…** menu) shows every saved version with a diff and **Restore**.
- Installing opens the setup wizard: bind each model slot, enter secrets (saved in General → Vault), connect the MCP servers, plugins, and tools it lists, install its dependencies (see **Dependencies** above), grant permissions, and answer any setup questions. Steps you skip leave the workflow marked **Needs setup**; you can finish later from its card.
- A workflow with agent steps adds an **Agents** step to setup: each agent it asks, marked **Shared** when it is a teammate's, reads **Reachable** or **Not reachable** with the reason (no agent by that name here, more than one, a shared agent you can no longer reach). **Choose…** keeps **As the workflow names it** or picks one of your agents (**On This Mac**) or an agent **Shared in Workspaces**; the choice stays on this Mac and never travels with the template. The agent must also be in **Allowed subagents**, the same list `spawn_agent` uses (Agents → Delegation for runs from the Workflows window and the Orchestrator, or the agent's own Subagents tab when a custom agent starts the run); setup reads **Not reachable** until it is, with **Add to Allowed subagents** to add it to the Orchestrator's list, and Edit Step notes it under the agent menu. **Allow Without Asking** lets this workflow's agent steps run without an approval card, so they also run in schedules and automations nobody watches. It is saved on the workflow and covers only its steps; Agents → Delegation → **Permission** and the Orchestrator's own hand-offs are unchanged. With it off, the step follows that Permission (a run a custom agent starts uses that agent's own Subagents tab). A **Deny** there still wins, a run a teammate starts always waits for your approval, and an update that asks a new agent turns it off until you allow it again. Shared agents are listed once the workspace rosters load; until then setup notes it is still checking rather than blocking.
- A plain key (not a sign-in or a connection) can wait: leave it empty and the workflow still installs. Its row reads **Not set**, its page shows **Keys missing**, and General → Vault → **Missing Keys** lists it until a value exists. Runs that need it stop with the keys it lacks and a pointer to the Vault.
- Workflows belong to no agent. A run uses the keys shared by all agents in General → Vault. When a custom agent runs it (its `workflow_<name>` tool, including a subagent the Orchestrator handed work to, an automation whose **Run as** names the agent, or a run started from Workflows in a custom agent's window that has it turned on), that agent's own value for a key overrides the shared one. The Orchestrator's `run_workflow`, the Architect, and a window with no agent always use the shared keys, even when the Orchestrator has its own values in the Vault. So one workflow can run with different keys for different agents: give an agent its own value in the Vault (the agent picker beside **All Agents**, then **Use a Different Value**). A nested **Workflow** step runs as the caller of the outer run.
- Secrets are saved in General → Vault under their name and shared: another workflow, MCP server or agent that asks for the same name uses the same value, and the Secrets step shows **Uses the shared NAME in the Vault**. Turn on **Use a separate value for this workflow** before saving to give one workflow its own value. Uninstalling a workflow keeps its keys (other things may use them); delete them in the Vault. Every value a run handles (install secrets and secret form answers) is replaced with `[REDACTED:KEY]` in the run record, logs, and output.
- **Connections** are the sign-ins and keys workflows share; each one is a *session* of its service ("GitHub · Work", "GitHub · Personal"). In a Secrets step, **Keep as a connection other workflows can use** saves the value you paste under a name, and **Sign in to <service>** saves the sign-in the same way (with **New session name** when the service already has one); later workflows see **Use the session “…”** for the same service instead of asking again, and the one you pick is that workflow's own. When the Architect built a step on your login to a service ("use my GitHub"), the secret already names that service: setup lists your existing sessions first, and a value you paste is kept as one by default. Which session a run uses: the calling agent's own session for that service when it has one (Vault → **Accounts**, **This agent uses**), else the workflow's pick. The Orchestrator, the Architect, a tab, and an automation without **Run as** always use the workflow's pick. The workflow's page shows it as **Session: Work · Scout uses Personal**. **Connections** in Main window → Workflows opens a sheet right there: each sign-in with its status, its service and the workflows that use it, with **Sign In Again** (or **Replace Value** for a pasted key), and **Needs Setup** for workflows still missing a sign-in, each with **Set Up**. Signing in again renews the same session, so every workflow and agent on it keeps working; in setup, **Sign In Again** on an expired session does the same. **Manage All Sign-Ins in Vault** opens Vault → **Accounts**, which also shows the agents that use each session and lets you rename it, make it the default, or remove it (the workflows that used a removed one ask for the secret again at setup). Values stay in the Keychain on this Mac and never travel with a template; plain secrets that are not connections are in General → Vault.
- Updating to a version that can reach new hosts, tools, MCP servers, plugins, or permissions re-asks every secret: the Secrets step marks each one **Confirm** with what changed, and **Keep Current Value** or a new value lets the update continue.
- A model slot whose suggested model is not here says how to get it without leaving setup: **Download** for a local model (with progress, pause, and cancel), **Connect <Provider>** for a cloud model whose provider is not set up, or **Browse Models** when Osaurus can't tell where it comes from. A slot that only prefers its model runs on your default model until then; the preview says so before you add it.
- Each MCP server the workflow uses gets a card in the **Tools** step. A server already here under another name ("Linear (work)" for "Linear") is used automatically, and its tools are called by their names here. Otherwise the card offers **Turn On** or **Connect** for a server that is set up but off, **Add <Service>** for one in the MCP Directory, **Set Up** from the template's connection details, or **Add Server** by hand. The picker on the card binds the server to any server here instead.
- If setup sends you to another tab (Models, Providers, MCP Servers), a toast offers **Finish Setup** once what it was waiting for arrives. When the template ships examples, **Run an Example** on the review step runs the one you pick after you finish and opens its run page in Workflows; nothing runs unless you pick one.
- Updating to a newer template version asks only about requirements that are new or blocking.
- An agent template can carry the workflows its agent calls (**Include Workflows** when saving). Using it adds a **Workflows** step to the agent setup: a workflow already installed at the pinned version or newer is reused, and the others are set up together with **Set Up Workflows…** (or **Update Workflows…**) before **Create**. That one pass asks for each workflow's model slots, then each shared secret, MCP server, plugin, and permission once, and **Install All** installs them together. **Use … for every workflow model slot** prefills each slot with the agent's model. The new agent starts with those workflows turned on.
- Creating an agent from such a template through the Orchestrator (`osaurus_config` with `template`) does not install workflows: it stops with `needs_setup` listing them, and you create the agent from its card in Settings → Agents → Templates instead. Once they are installed, the Orchestrator's plan turns them on for the new agent.
- A workflow's page (**See all runs** under its row in Main window → Workflows, or **Details & History** in its **…** menu; Esc, ⌘[, or the back button in the title bar returns) opens with the workflow's name, summary, a **Ready to run**, **Keys missing**, or **Needs setup** badge, its step count, and whether it **Runs on this Mac** or **Uses the cloud**. Below that: **Runs** (live runs first, then the last five, **Show All** for more and **All Tasks** for Tasks → History; click one to open its run page with its steps and result, the failed step already open; Architect test runs stay out of this list and out of the step badges' time and token averages), **What It Does** (what you give, each step in run order with its step badges — hosts reached, files written, shell or browser use, local or cloud model, and the time and tokens recent runs took — and what you get; **Open Full View** in its corner shows the steps as a graph, see **The full view**), **Before It Runs** (what still needs setting up, and what it uses: the model it runs on, for example "Apple Foundation Models (this Mac)", keys, tools, and internet access, with **Set Up…** or **Change…**), **Who Can Start It** (**Osaurus can run this for you**, **Teammates can run this**, **Fix repeated failures automatically**, and the agents that have it turned on), **Tags** (your own comma-separated labels, such as "finance, weekly"; **Add Tags** or **Edit**, then **Save** or Return; they stay on this Mac and are not exported), **Saved Answers** when the workflow remembers any (review or clear remembered form values), **Stored Data** when the workflow has a state step or has stored something (the tables it keeps between runs — key, value, when it changed — with **Clear** per table or **Clear All**). The tool name agents call it by is under **Advanced**. The footer has **Share…** (or **Manage Published…**), **Rename…**, **Edit** (opens the workflow in the Architect, the same as **Edit with the Architect** in its **…** menu), and **Run**.
- **Renaming.** A workflow's name is what Settings shows, what custom agents call (`workflow_<name>`), and what the Orchestrator's `run_workflow` and automations name; it is separate from its template's name. **Rename…** (in the detail page's footer and the card's **…** menu) shows the tool name before and after, the numbered name a taken name becomes, and the workflows that run this one as a step. Renaming the draft in the Architect and saving renames the workflow too; the save prompt says so and names the new tool. An update never renames a workflow on its own: the Update wizard's review step has a **Workflow Name** field that keeps the current name unless you take the new version's (**Use “…”**). When the version a workflow runs carries another name, its card shows **Name differs** and its page offers **Use “…”** or **Keep “…”**. Old names keep working: a Workflow step, the Orchestrator, or an older config file that names the workflow by a name it had before still finds it.

Inference steps need a model with **native structured output**: a cloud provider that enforces JSON schemas, Apple Foundation Models, or a local MLX model whose tokenizer supports grammar-constrained decoding (byte-level BPE, which covers most current bundles). A local model runs the step in its native non-reasoning mode. A step whose output is one text field is written as plain text and becomes that field; for any other output every token is checked against the step's schema as it is generated, and the step's fields are described to the model. A model that can't do this (for example one with a SentencePiece tokenizer) shows a blocking setup item instead of running with unchecked output. Local steps use the JSON Schema subset the runtime enforces: `type`, `properties`, `required`, `additionalProperties`, `items`, `minItems`/`maxItems`, `enum`, `const`, `anyOf`, and local `$ref`; a step whose schema uses `pattern`, `format`, length or numeric bounds fails with a message naming the keyword.

## Running a workflow

- **In Workflows**: **Run** on a workflow's row in Main window → Workflows starts it at once when it needs no input; otherwise a sheet asks for it. Picking a workflow in the inspector's Workflows lens, a notification, **Open Run** in chat, or **Try It** after saving opens its run page in Workflows (Esc, ⌘[, or the back button in the title bar returns). The page says what you fill in, how many steps it takes, and what you get. Required fields carry a **\***, each field's help sits under it, and **Fill with Example** fills the form from the template's examples. **Run** (⌘Return; then Stop and Run Again) stays in the footer below the form. Each field of the **Result** has its own copy button, and **Copy All** in the Result header copies every field at once (**Copy** when the result is raw JSON; absent when there is only one field). During a run every step is one row in run order, with an icon for its state and how long it took; under the name it reads waiting, working…, skipped, or failed (a finished step needs no word); a step that needed more than one try shows **Retried ×N**, and a failed run says which step it stopped at. Click a row to open it: its model, tries and tokens, the images it made, its input and output (left out when empty, and behind **Show input and output** for an image step), its log, requests, and tool calls. An image step that is still working reads **Image step 12 of 30** with the time left. While a model step works, the text it has produced so far shows under the step and grows as tokens arrive (for models whose backend applies the output schema while streaming: local MLX and cloud providers; Apple Foundation Models and Claude Code deliver the whole answer at once); it is replaced by the step's output when it finishes and is not kept in history. The result shows each output field under its title, text rendered as Markdown, with a copy button on each field and **Copy All** for everything. **Run Again** starts it again at once when it takes no input, otherwise goes back to the form with the same inputs. **Runs** beside the run's title lists past runs. A run that was still going when Osaurus quit picks up where it left off after relaunch: finished steps keep their results, unfinished steps run again, and a form that was waiting is shown again with the time it had left. A test run, or a run whose workflow was removed, changed, or needs setup since, shows as cancelled instead.
- **From chat**: type `/` and pick one of the current agent's workflows (listed by name) to open its form in Workflows.
- **From an agent**: in Settings → Agents → (custom agent) → Abilities → **Workflows**, turn on the workflows that agent may call; a workflow that lacks a key for that agent (neither its own nor a shared one) shows **Missing keys: NAME**, which opens the Vault on that agent. Each becomes a tool named `workflow_<name>` whose arguments are the workflow's input, and the run uses that agent's own keys first. The agent waits for the run and gets its output (or the failure) as the tool result. While it waits, the tool card in chat follows the run the way its run page does: each step as it starts and ends, and the text a model step has produced so far; the card ends with the run's outcome. Tool rows in chat have an **Open Run** link.
- **From a teammate**: someone chatting with one of your shared agents (a workspace member, a guest, or a teammate's agent) can start a workflow that agent has turned on only when **Teammates can run this** is on for it (the workflow's page, **Who Can Start It**; off by default). The run is on your Mac with your keys, connections, and folders, so each call asks you first through the agent's **Require Approval for Teammate Tool Calls** (Workspaces → *workspace* → Shared Agents); with that off, the call is declined. A workflow not open to teammates is refused before anything starts, and the agent tells them its owner hasn't allowed it. A form the run stops for waits for *you* on this Mac, not the teammate. The run's caller names the teammate and workspace, and the workspace audit log records each start, finish, and refusal. To give teammates their own copy instead, publish it to the workspace (see **Workspace** under Installing and setup).
- **From the Orchestrator**: it lists every installed workflow (`osaurus_config` action `workflows`, each marked `orchestrator_can_run`) and runs the ones marked **Osaurus can run this for you** with `run_workflow`. It can turn workflows on for a custom agent (`agents[].workflows` in `osaurus_config`) and start any installed workflow from a trigger by applying an `automations:` entry with `workflow:` and `input:` ("run Daily Digest every weekday at 8"). Asked to build a new workflow that runs on its own, it hands off to the Architect with the trigger in the brief; the Architect's save card then offers to set that trigger up.
- **From an automation**: Settings → Automations → Add Automation → **Run Workflow** starts the workflow when a schedule, folder change, webhook call, new feed item, stream message, failed run or app event happens (see the Automations guide). A channel message starts one through a rule in Channels → the channel → **Routing** instead. Each input field is mapped from what started it (`{{text}}`, `{{webhook.body.issue}}`, `{{message.sender_id}}` …); the mapped input is converted to the field types and checked against the workflow's input schema before the run starts, and a mismatch is recorded on the automation's **Runs** (and in Automations → History) as `invalid_input`. The run's caller is `event` (`{{caller.kind}}`). **Run as** chooses whose keys and sessions the run uses: **No agent (shared keys)** (the default) or a custom agent, which need not have the workflow turned on; the automation's page shows **Runs as** with the agent. A message automation can send the workflow's output back to the conversation; when a **Reply** step already posted in that conversation, the output is not sent a second time (a failed run still says it failed). A run that stops for a form frees the automation for its next run; the automation's run row follows it until the form is answered. When a channel message started the run, the form is also asked in the conversation, one question at a time (see the Channels guide).
- **Background tasks**: when a background task's workflow stops for a form, the task shows *Waiting for input* and a notification opens the run. When the run ends, the task continues with the result; a task that started several workflows in one step waits for all of them. Stopping the task cancels the waiting runs. The task's chat remembers what it was waiting on, so a run answered after a relaunch still lands in it.
- **From the HTTP API or MCP**: a caller outside the app cannot wait for a form. When a run stops for one, the call returns `awaiting_user` with the run id and a notification opens the run; it finishes on its own once the form is answered. `GET /workflows/runs/{run id}` returns the run's result once it ends (and its waiting form while it does not). A run your iPhone starts through Sync waits as it does in chat. Workflow tools and `run_workflow` are not listed on `/mcp/tools` for callers with no chat agent bound. Off this Mac, the run and form routes need the Secure Channel.

Before every call Osaurus re-checks setup for that caller. If something is missing (a removed model, a revoked secret, a disconnected MCP server, a tool no longer on this Mac) the call fails with `needs_setup` and the reasons, and the workflow is marked **Needs setup** until it is fixed. A workflow whose file in `~/.osaurus/workflows/` was edited outside Osaurus reads **Changed outside Osaurus** and does not run until you open **Set Up…**, review its steps, and finish setup. A key the caller lacks is checked against that caller's own value, then the shared one; when only keys are missing, the call points to General → Vault and the workflow is not marked **Needs setup**, since another agent or the shared keys may have them. On a run page, the footer says **Uses shared keys** or **Uses <agent>'s keys**, and a run missing keys shows **Open Vault**. A step that reaches a key with no value fails with `missing_key`.

A failed run opens with where it stopped and why, under the name of the step, with **Fix with the Architect** beside it. Each step expands to its model, tools, output, and errors.

### The full view

**Open Full View** (the arrows in the corner of the Architect's **Steps**, a workflow page's **What It Does**, and a run page's **Steps**) opens the whole flow as a graph over the window, on its own large sheet; closing it leaves the window's size alone. It reads left to right like a story: **You give** on the left (the fields you fill in, or what you filled in for the shown run, else "Nothing to fill in"), the steps in the middle, and **You get** on the right (what the workflow hands back: the fields it will have, or the run's result; while it runs, "On its way…"; if it failed, the step where it stopped). Steps that run at the same time stack in one column under "These N run at the same time", and the columns are ordered so lines cross as little as they can. Each step is a card with an icon tinted by its kind (AI, code, the web and tools, for-each, other workflows, people, media), its name, and one line saying what it does (or, if it failed, what went wrong, in red; "Not needed this time" for a branch the run passed by). Small icons along its bottom show what it reaches (the web, a cloud model, secrets, files, commands, a browser, the Mac); hover one for the details. Once it has run, its border takes the color of how it went and its time sits in the corner. It opens fitted to the window; a flow too long for it opens at a readable size on its first step, and 0 or the fit button shows all of it.

- **What moved.** Once a step has run, a chip on the line leaving it says what it made: "20 items", the first line of what it wrote, or the image it made. Click the chip to see all of it. Lines that only run when a condition holds are dashed, with "If …" near the step they lead to.
- **Where your data goes.** A chip in the top bar says, for the whole workflow, **Stays on this Mac**, **Goes online**, **Uses a cloud model**, or **May leave this Mac** (a step's model isn't chosen yet, or it falls back to a provider when this Mac has no model). When something leaves, click the chip to dim every other step; click it again to show them all.
- **Following a run.** From a run page it shows that run; from the Architect, the latest test. While the run goes, a moving dash runs along each line into the step that is working, a working step's border pulses and its card shows the last lines its model has written or the image forming, finished steps settle with a check and their lines turn green, and branches the run did not take fade. A step waiting on a form reads **Waiting for you**, and the form itself floats in the bottom-left corner of the canvas, the same one the run page shows; **Continue** answers it without leaving the full view. With Reduce Motion on, nothing moves: working lines are drawn solid instead.
- **Map steps** look like a stack of cards and read "Repeats for each item, N at a time", with how many items are done, working, and failed. The chevron opens a dot per item (up to 400, then "and N more") that fills in as items finish; click a dot for that item's result or error. Item progress is only shown live; once the step ends, the dots come from its output.
- **Workflow steps** open in place: double-click one, or **Open** on its card or in its details. From a run it shows the run that step started, else the workflow itself. The title becomes a trail of workflow names; click one, or press Esc, to go back out. **Open** is greyed out when this Mac doesn't have that workflow.
- **Focus.** Click a step to select it; with focus on (the scope button, or F), the step, everything it depends on, and everything that depends on it stay bright and the rest dims. Zoomed out below 60%, steps shrink to pills.
- **Getting around.** Scroll to pan; pinch, + and −, or the zoom buttons to zoom; 0 or the fit button to fit (⌘= and ⌘− still change the app's text size). When the graph is larger than the window, a minimap in the corner shows where you are; click or drag in it to move. ⌘F finds steps by name, what they do, or kind: matches stay bright, Return and Shift-Return go to the next and previous. The arrow keys move along the lines (left and right) and within a column (up and down). Click a line to see what went along it in the run and when it is taken.
- **A step's details.** Selecting a step opens a pane on the right; the X in its corner, clicking empty canvas, or clicking the step again closes it. It says what the step does and how it went ("Done in 2.4 s"), and for a run: **What went wrong** and **What you can do** when it failed, **What it got** and **What it made** as readable fields (**Show Raw Data** for the exact data), **Where your data goes** (its model and what it reaches, or **Stays on this Mac**), and **Then** (where it goes next; click one to go there). **More Details** holds the kind, model, tries, tokens, the tools it used, and the step ID. For an Architect draft it has **Runs on**, **Edit Step…**, and the **…** menu (**Ask the Architect** closes the full view and starts the message in the chat). Esc closes the full view.

## Auditing runs in Insights

Every run is recorded in Insights (Settings… (⌘,) → Insights, **Workflows** scope tab): one **Workflow run** row per run (workflow, caller, status, input, output, duration) and one **Workflow step** row per finished step (input, output, model and tokens, tool calls with their arguments and results, logs, and requests). The model calls, tool calls, and network requests a step makes carry the run too. A run row's details have **Open Run** (the run in its workflow tab) and **All Events for This Run** (every row the run wrote); any row made inside a run shows **Workflow run** under who made it. The chart icon in a run's header, in a workflow tab, the Architect's test, or **Recent Runs** on the workflow's page, opens its row in Insights. Inputs, outputs, and logs follow Privacy & Security → Activity Log → **Store Prompts and Responses** like every other row.

## Osaurus Beta and going back

Osaurus Beta installs next to Osaurus and uses the same data folder (`~/.osaurus`), so chats, agents, models, and settings are the same in both. Only one can be open at a time: opening one while the other runs asks you to quit the other first (**Quit Osaurus** or **Quit Osaurus Beta**).

To go back, quit Osaurus Beta and open Osaurus. Nothing needs reinstalling, and nothing is deleted. In Osaurus you will find:

- Your chats (including the ones you had in the beta), agents, memory, models, providers, and settings.
- Schedules, watchers, and channel routing (which agent answers Discord, Slack, Telegram, iMessage, WhatsApp, and n8n messages) as they were when you first opened the beta. The beta copies them into Automations and leaves the originals in place.
- Insights, with every row except the beta's workflow and automation rows. **Verify Integrity** reports those rows as unreadable because Osaurus does not know their kind; they are intact and verify cleanly in Osaurus Beta.

Workflows, workflow runs, and automations created or changed in the beta do not appear in Osaurus; they stay in the data folder and come back when you open Osaurus Beta again. Changes you make in Osaurus to schedules, watchers, or channel routing do not reach the beta's Automations. Saving a custom agent in Osaurus clears the workflows turned on for it in the beta (Settings → Agents → (agent) → Abilities → **Workflows**); turn them on again there.

## Tips

- Keep input schemas small and explicit; they become the tool's arguments. Give each field a `title` and a one-line `description`, and list the fields in `x-order` in the order a person fills them in. The Architect does this for you; when a schema has no `x-order`, required fields come first.
- Use *remember* on dialog fields that rarely change (an account name, a default folder) so repeat runs skip them.
- A saved or published template never includes secrets, saved answers, or local paths. Turn on **Include how to connect my MCP servers** when you share so the person you send it to can add each server in one click.
- A published workflow's page shows every step, the full source of code steps, network hosts, the secrets it asks for (never their values), tools, and models to whoever can see it: everyone for **Public**, people with the link for **Unlisted**, people with the password for **Password**. Publish shows the same review before anything is uploaded.
